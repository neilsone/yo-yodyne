# Working Agreement: Review Process

**Scope:** All units
**Date:** 2026-03-08

---

## Purpose

Ensure quality and alignment without bottlenecking creative or technical work.

## Standards

### What Gets Reviewed

| Artifact | Reviewer | Review Focus |
|---|---|---|
| OPSX proposals | PI | Alignment, scope, impact |
| Delta specs | Affected unit(s) | Accuracy, completeness |
| Code changes | Engineering | Correctness, standards compliance |
| Content for publication | Production + PI | Accuracy, brand consistency, engagement |
| Creative deliverables | Requesting unit (limited scope) | Technical requirements only — NOT creative choices |

### Review Boundaries

Per the Creative Autonomy Principle:
- Reviews of creative work SHALL assess technical requirements and factual accuracy only
- Reviews SHALL NOT override creative decisions (composition, tone, style, aesthetic)
- See `openspec/specs/creative-autonomy/spec.md` for the full principle

### Process

1. Author creates a PR or submits artifact for review
2. Reviewer assesses within their permitted scope
3. Feedback is provided as suggestions, not directives (for creative work)
4. Author addresses feedback or explains their reasoning
5. Reviewer approves or escalates to PI

### Turnaround

- Reviews SHOULD be completed within 1 working session
- Blocking reviews MUST be flagged in the dependency registry

## Exceptions

- Alpha releases require PI review only (lightweight)
- Trivial fixes (`fix: typo`) may be self-merged with a note

## Review

Adjusted if the review process becomes a bottleneck or fails to catch issues.
